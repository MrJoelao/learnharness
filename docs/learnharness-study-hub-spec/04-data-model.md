# 04 — Data model and persistence

## 1. Core principles

- Chat transcripts, workspace metadata, plugin-owned state and organization metadata remain separate.
- A workspace is not a chat record.
- Organization metadata is presentation/placement metadata only.
- Archiving/moving/reordering must never rewrite workspace domain state.
- Preserve `ChatOrganization` v1 if possible; do not casually introduce a destructive migration.

## 2. Existing organization model

The inspected source currently defines:

```ts
interface ChatOrganization {
  version: 1;
  folders: ChatFolder[];
  placements: Record<string, ChatPlacement>;
}

interface ChatPlacement {
  folderId: string | null;
  archivedAt?: string | null;
  order?: number;
}
```

The placement map is keyed by string ID and is already structurally capable of holding non-chat IDs. However, current public/internal action types and directory projections still use chat-specific terminology and `kind: "chat" | "folder"`.

Do not conclude that arbitrary IDs are fully supported merely because `placements` is generic.

## 3. Directory model

Generalize the directory output to a common discriminated union.

Suggested shape:

```ts
type DirectoryEntry = ChatDirectoryEntry | WorkspaceDirectoryEntry;

interface ChatDirectoryEntry {
  kind: "chat";
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  folderId: string | null;
  order?: number;
  archivedAt?: string | null;
  // Existing chat-specific summary fields remain available.
}

interface WorkspaceDirectoryEntry {
  kind: "workspace";
  id: string;
  title: string;
  pluginId: string;
  modeId: string;
  icon?: string;
  createdAt: string;
  updatedAt: string;
  folderId: string | null;
  order?: number;
  archivedAt?: string | null;
  availability:
    | "available"
    | "plugin-disabled"
    | "plugin-missing"
    | "mode-missing";
}
```

Potential directory container:

```ts
interface LearningDirectory {
  organization: ChatOrganization;
  entries: DirectoryEntry[];
}

interface ArchivedLearningDirectory {
  folders: ChatFolder[];
  entries: DirectoryEntry[];
  activeFolders: ChatFolder[];
}
```

Names should follow existing conventions. Do not retain misleading `chats` property if it now contains workspace entries. If changing a public/internal function shape risks compatibility, add a new generalized API and keep the old chat-only adapter temporarily.

## 4. Organization actions

Generalize item actions from `kind: "chat"` to `kind: "entry"` (or a better domain name) while preserving folder operations.

Conceptual actions:

```ts
type OrganizationItemKind = "chat" | "workspace";

type OrganizationAction =
  | { action: "move-entry"; kind: OrganizationItemKind; id: string; parentId: string | null; targetOrder?: number }
  | { action: "reorder-entry"; kind: OrganizationItemKind; id: string; targetOrder?: number; targetIndex?: number }
  | { action: "reorder-entry-siblings"; parentId: string | null; kind: OrganizationItemKind; ids: string[] }
  | { action: "archive-entry"; kind: OrganizationItemKind; id: string }
  | { action: "restore-entry"; kind: OrganizationItemKind; id: string; targetParentId?: string | null }
  // Existing folder actions remain.
```

Do not rename existing API action strings if they are consumed externally. If the organization action route is internal-only, inspect all callers and tests before deciding whether to generalize in place or introduce a versioned/internal adapter.

### Required invariants
- Entry ID must exist in the authoritative set for its kind, or be a known placement under a documented recovery rule.
- A chat ID cannot be treated as a workspace ID and vice versa.
- Folder cycle prevention remains unchanged.
- No item can be moved into an archived folder.
- Reorder operates only on siblings of the same parent and kind semantics.
- Folder deletion is allowed only when there are no child folders and no active or archived entries placed in it, unless existing product behavior explicitly supports another rule.
- Folder archive/restore cascades consistently to all descendant entries, both kinds.
- Restoring an entry to a missing folder must use a documented fallback (root) or return a validation error. Never silently orphan it.
- Placement cleanup on permanent deletion must remove only that entry's placement.
- A workspace archive does not delete its metadata or plugin state.

## 5. Workspace host metadata

Suggested schema:

```ts
interface WorkspaceRecord {
  version: 1;
  id: string;
  pluginId: string;
  modeId: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  state: "ready" | "creating" | "error";
  lastError?: {
    code: string;
    message: string;
    occurredAt: string;
  };
}
```

Rules:
- `id` is generated by the host and globally unique.
- `(pluginId, modeId)` references the registered definition, not a display name.
- `title` is user-editable and must not be overwritten on plugin updates.
- `updatedAt` changes when host metadata changes, not on every plugin storage write unless that is an explicit product decision.
- `state` must not encode plugin enabled status; availability is derived at runtime.
- Do not store the plugin's full state in this record.

## 6. Storage layout

Proposed logical layout (adapt to the repository's existing data root and safe path resolver):

```text
<learning-data>/
  workspaces/
    index.json                 # Optional index; may be derived instead
    <workspace-id>.json        # Host-owned WorkspaceRecord
  plugins/
    <plugin-id>/
      data/
        workspaces/
          <workspace-id>/
            state.json         # Plugin-owned
```

Core plugins may use the existing `core-plugin-data/<id>/` writable root rather than community plugin path. Always use existing origin-aware path APIs. Never derive writable paths from untrusted strings or expose raw paths to frontend plugins.

Prefer one source of truth. If `index.json` is used, define atomicity/recovery. Avoid maintaining redundant index and per-record copies unless needed for performance.

## 7. Versioning and migration

- Keep `ChatOrganization.version: 1` if its structure remains compatible.
- If semantics change, document why old readers/writers remain safe. A generic placement key does not itself require a schema bump.
- Add a new schema version only when the serialized shape or interpretation changes.
- Unknown newer versions must be rejected for writes, not overwritten with defaults.
- Workspace metadata has its own version.
- Plugin-owned workspace state is migrated only by its owning plugin.
- Migration must be tested with old organization files, missing placement records, malformed records and unknown versions.

## 8. Deletion policy

For the initial release, avoid automatic destructive deletion:
- Archive is reversible and preserves all data.
- Permanent workspace deletion, if implemented, must be an explicit user action with clear confirmation.
- Plugin uninstall/disable must not delete workspace records or plugin data.
- Do not automatically delete orphaned data.

## 9. Sorting

Use one shared sibling sorting function for chat and workspace entries:
1. Explicit numeric `order` first.
2. Stable deterministic tie-breaker.
3. For entries without explicit order, use `updatedAt` descending, then stable ID.
4. Never let asynchronous plugin loading reorder the tree unpredictably.

Keep the current UX's ordering behavior where possible and test mixed chat/workspace sibling ordering.
